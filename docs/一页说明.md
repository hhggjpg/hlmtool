# 红楼梦人物关系分析工具 —— 一页说明

> **【摘要｜只想知道结论的话看这一段就够】**
>
> **用了什么模型**：DeepSeek `deepseek-flash`。中文原生、便宜、接口兼容 OpenAI 格式。
>
> **花了多少钱**：约 9 元（384 万 token；预算 1000 元）。整本书跑一遍不到一杯奶茶钱。
>
> **做出了什么**：全 120 回跑通，抽出 497 个人物、2022 条关系，
> 每条关系都带原文依据，**忠实度 99.3%**。产出人物表、关系表、关系图和关系演变清单。
>
> **最难的一关**：第 85 回抽取出空文件。排查发现是**模型在特定文本上陷入"复读"**，
> 输出顶到 65536 token 上限被截断、返回空内容，而脚本把空内容当成功写进了文件。
> 解法是写补丁脚本把该回切成两段抽取再合并。
>
> **最大的教训**：**先用全量数据跑一遍，再回头调参。**
> 前 5 回跑得很好，让我以为流程已经稳了；真正跑 120 回才发现别名不够、
> 通称混入、标签爆炸、图糊成一团、还有一回直接空文件——
> 这些问题在前 5 回里一个都看不到。

## 一、用了哪个模型，为什么

用 DeepSeek 的 deepseek-flash（实际对应 DeepSeek-V4.1-Flash）。三个理由：

1. 中文原生，读古典白话文不需要额外处理。
2. 价格低：输入 0.3 美元/百万 token、输出 1.2 美元/百万 token，低谷时段减半。
3. 获取，使用apikey简单


一个实测发现：这个模型默认开启"思考模式"，输出前会先生成一段内部推理。
全 120 回的用量里，**输出是输入的 4.7 倍**（输入 676,039，输出 3,170,013），
绝大部分 token 花在"想"而不是"写"上。这是最主要的成本来源。


## 二、一共花了多少钱

【总共花了9元，56,222,586Tokens】 ← 以平台账单为准

参考数据（来自本项目的 output/run_log.txt）：

- **全 120 回抽取：输入 676,039 + 输出 3,170,013 = 合计 3,846,052 tokens**
- 按 DeepSeek 标准价估算（输入 ¥2/百万、输出 ¥8/百万）约 ¥26.7
- 另加：首次调用测试、重跑、第 85 回分段补抽等零星消耗

预算 1000 元，实际远未用尽。**整本书跑一遍不到一杯奶茶钱**，
所以"多试错几次"的成本压力几乎不存在——这一点在做之前没预料到。

单回波动很大：最短的一回输出 1.2 万 token，最长的一回输出 6.5 万
（就是第 85 回"复读失控"那次，见下面第 8 条）。


## 三、中间哪里卡住了，怎么解决

### 起步阶段（9 月 16 日，第一次碰 Python）

1. cmd 里敲 python --version 完全没有输出（不报错、不返回）
   原因：WindowsApps 目录里有个 0 字节的占位文件排在 PATH 前面，
        把真正的解释器挡住了。
   解决：设置 → 应用 → 高级应用设置 → 应用执行别名，关掉 python.exe。
   排查手法：用 where python 命令列出系统找到的所有同名程序及其优先级。

2. VS Code 打开新文件夹后打不开终端
   原因：工作区信任（Workspace Trust）的"受限模式"会禁用终端、
        调试和部分扩展。
   解决：点顶部横幅上的 Trust this folder。

3. 激活虚拟环境时被拒绝（PSSecurityException：禁止运行脚本）
   原因：PowerShell 执行策略默认是 Restricted，不允许运行任何脚本文件。
   解决：Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

### 取文本阶段（9 月 19 日）

4. 取文本时维基文库打不开（ERR_TIMED_OUT）
   原因：该站在本地网络环境下连接不稳定，不是网址错、也不是操作错。
   解决：换用 purepen.com（纯文学网站）。换源前先查了它的 robots.txt，
        确认为"Disallow:"（空），即允许抓取。换源后还发现它的正文
        已是简体中文，省掉了原计划的繁转简步骤。
   （后续：跑全本时最终改用 GitHub 公开仓库的程高本，原因见第 7 条。）

5. 文本中发现 14 处字符缺失（显示为方框）
   原因：老式中文网站把无法编码的生僻字塞进了 Unicode 私有区
        （U+E000–U+F8FF），属于源头缺陷，不是复制失误。
   解决：写脚本扫描全部文件，定位全部 14 处，
        确认全部落在描写性文字（服饰、器物、诗句）中，不涉及人名，
        最后决定不修正，保留数据的可追溯性。

6. 安装依赖时包被装进了全局 Python 而不是项目虚拟环境
   原因：执行 pip install 时虚拟环境未激活；屏幕上看不出任何异常，
        但包实际装到了别处。
   解决：先激活虚拟环境（确认命令行提示符前有 (.venv)）再安装。
        排查手法：python -c "import sys; print(sys.executable)"
        看输出的路径里有没有 .venv。
   附加：这一条是在"换目录验证"环节抓出来的——代码没有 bug，
        是 README 缺少警告。已在 README 第 3 步补上提示和自检命令。

**以下是跑全 120 回时才暴露出来的问题（前 5 回根本不会出现）。**

### 全本阶段（10 月 4–5 日：跑 120 回时才暴露的问题，前 5 回一个都看不到）

7. 换数据源：手抄的 5 回与新抓的 120 回不是同一个版本，必须全部弃用
   现象：最初手工复制了 5 回（来自一个网页版本），后来为了跑全本改成
        从 GitHub 公开仓库抓程高本 120 回，两边内容对不上。
   排查：写脚本把两份文本去掉空白后逐字对比，**相似度只有 78.9%**
        （第 1 回字符数 7775 vs 6733，差 1000 多字；标点、虚词、标题写法都不同）。
   结论：**不能混用**——同一个人的出场次数会统计不准，
        而且验收时"前 5 回和后面不是同一个版本"会被当场问住。
   解决：120 回全部重取，前 5 回也重新抓；旧文件备份到
        data/raw_backup_manual/ 留作对照，不删除。

8. 第 85 回抽取出空文件：模型陷入"复读"，输出顶到上限后返回空内容
   现象：output/chapter_085.json 是 0 字节；重跑一次还是 0 字节。
   排查：
     ① 数文件大小，发现 016 和 085 两个 0 字节文件；
     ② 看日志，两次都是 completion=65536 / 65538——精确卡在 65536（2 的 16 次方）；
     ③ 查原文长度，085 回只有 8000 字、排第 31 名，不是最长的——
        排除了"内容太长抽不完"这个最直觉的解释；
     ④ 写诊断脚本，只把正文的"前半段"发过去，结果 finish_reason=stop、
        正常返回了完整 JSON。
   结论：不是代码错、也不是原文有问题，是模型在特定文本上会陷入
        重复循环（业界叫"退化"），一直吐到上限被截断，content 变成空字符串。
        而脚本把空内容照样写进文件并报告"完成"——属于**静默失败**。
   解决：写 scripts/fix_085.py，把该回切成两段分别抽取再合并
        （人物去重、关系拼接），最终得到 25 个人物、29 条关系。
   教训：**崩掉的 bug 是好 bug，静默失败的才是真麻烦**。
        这也是 check_outputs.py 和 verify_all.py 存在的意义。

9. 别名合并在全本尺度上彻底不够用
   现象：人物表里同时出现"贾母"(1686 次) 和"老太太"(975 次)，其实是同一个人；
        还有"林姑娘"/"林妹妹"/"黛玉"三行、"凤姐"/"凤姐儿"两行……
   原因：ALIAS 字典是在前 5 回上手工配的（只覆盖 19 条），
        那 5 回里模型只用"贾母"、从没用过"老太太"。
        到 120 回，模型开始用各种称呼，字典完全配不上。
   解决：把别名表从 19 条扩到 200+ 条。改完后：
        贾母 1686 → 2752，王熙凤 1762 → 2051，贾宝玉 3987 → 4498。
   教训：**在小样本上调好的东西，换到全量数据上大概率要重做。**

10. 通称和姓氏被当成了人名
   现象：人物表里出现"老爷"(641 次)、"张"(446 次)、"小丫头"(289 次)、
        "哥哥"(231 次)、"大夫"(126 次)……
   原因：模型把"一个老爷走进来"里的泛称也当成人物抽了出来。
        这类词根本不是具体某个人，画进关系图就是纯噪音。
   解决：新增 GENERIC 黑名单（通称 / 身份 / 姓氏 / 神话框架），
        在生成人物表和关系表时统一排除。

11. 关系图的节点数爆炸，图变得没法看
   现象：全 120 回抽出 497 个人物，全画上去就是 400 多个节点，
        中心区域糊成一团、一个字都看不清。
   原因：每回都会抽出几十个只出场一两次的小角色（丫鬟、小厮、路人）。
   解决：改 draw_graph.py，先读人物表，只保留出场次数最多的前 60 人
        （脚本开头的 TOP_N 可调）。改完后是 59 个节点、234 条边，
        结构一眼能看清：贾宝玉居中，贾母/王夫人/王熙凤/林黛玉/薛宝钗环绕，
        外圈是丫鬟和旁支。

12. 关系标签的"长尾"比预想严重得多
   现象：classify.py 的映射表只能归掉 21% 的关系，1626 条归不进任何一类。
   原因：前 5 回模型总共只生成了 40 多种标签，手工写个映射表就行；
        120 回模型生成了 **1007 种**不同标签——"吩咐""命取杯""君臣"
        "称谓：姐姐""二老爷跟前人养的"……**前 200 个标签加起来才覆盖 46%**，
        靠逐个补字典根本补不完。
   解决：把 classify.py 从"逐字匹配"改成"**关键词归类**"——
        看标签里含有什么词来判类。改完后未分类从 78.5% 降到 40%，
        可画图的关系从 445 条涨到 827 条。
   顺带发现：还有一类标签根本不是关系，而是"称呼"
        （"称谓：姐姐""称宝姐姐"）。这些边画进图里毫无意义，已单独归为
        "称谓"类、不画图。
   教训：**规则要跟着数据的规模变形，不能一条道走到黑。**


## 四、如果重做一遍，会改什么

1. 重新平衡提示词的"精度与召回"
   现在的第 1 条要求是"只抽原文中明确写到的关系"。好处是不编造，
   代价是漏掉隐含关系——贾母与贾宝玉这对祖孙，
   前五回未直接写明，所以图上没有这条关系。
   改法：分两轮抽取。第一轮抽显性关系，第二轮专门抽隐含关系，
   结果分开标注，由使用者决定是否采信。

2. "逐字连续摘抄"这条约束还不够严
   实测 123 条引用里有 1 条属于"裁剪拼接"：模型把一段长原文拆开、
   两头粘起来当引文，用词全是原文的，但连不成一句。
   改法：明确写"允许重复引用同一句原文，不要为了区分而裁剪"
   （这一版提示词已写好，编号 v3，未使用）。

3. 关系类型应该一开始就定死枚举值
   模型自由发挥生成了 40 多种标签（"岳婿""内兄""妹丈"
   "长官与门子"……），后来靠映射表才收敛到 5 类。
   期间还发现"林如海—贾政"同时出现"内兄"和"妹丈"两种标签，
   其实是同一层关系从两个人各自角度说的。
   改法：在提示词里直接给出可选的类别清单，不让模型自由命名。

4. 数据结构要加"方向"和"阶段"两个字段
   现在无法表达"黛玉对宝钗不忿、宝钗却浑然不觉"这种单向关系，
   也无法表达"贾雨村与门子过去是贫贱之交、现在是上下级"这种
   阶段变化。

5. 别名合并应做成"半自动"
   目前是纯手工维护别名词典，边跑边漏——"可卿"就漏过一次，
   导致人物表里一度出现两个秦可卿。
   **跑完全本后这条变得更加迫切**：字典从 19 条扩到 200+ 条全是手工写的，
   而 497 个人物里肯定还有没合并的（"元春"和"贾元春"就没对上，
   导致图上"元春"这个节点是孤立的小点）。
   改法：让脚本先按人物共现情况给出候选对，人工只做确认。
   更彻底的做法：让模型对"这两个名字是不是同一个人"批量判断一遍，
   结果存成表，人工抽查即可。

6. **先用全量数据跑一遍，再回头调参**（本次最大的教训）
   前 5 回跑得很好，让我误以为整个流程已经稳了。
   真正跑 120 回才发现：别名不够、通称混入、标签爆炸、图糊成一团、
   还有一回直接空文件。**这些问题在前 5 回里一个都看不到。**
   改法：以后拿到新任务，**先想办法用全量数据跑一次"最小版本"**，
   哪怕结果很烂，也要先让问题暴露出来，再决定往哪儿投时间。
   好在这类项目的试错成本极低（跑一遍全书不到 30 元），
   没有理由不做这一步。

7. **提示词里应该直接限定关系类别的枚举值**
   （这是第 3 条的强化）全本实测生成了 **1007 种**标签。
   如果一开始就在提示词里写"关系类型只能从以下 5 类里选"，
   后面根本不需要写 200 行归类规则。
   改法：在 `prompts/` 里加一版，把类别清单直接写进要求。
   预期效果：未分类从 40% 降到接近 0，而且省掉一整个脚本的维护成本。
